# 我试图让 AI 学会"不遗忘"，撞了三次墙后搞明白的三件事

这几个月我一直在折腾同一个问题：怎么让 AI 学了新东西别把旧的忘了。

先做的参数层面（持续学习里的灾难性遗忘），撞墙；换到优化层面，又撞；最后把同样的思路搬到 Agent 记忆上，再撞。

三次撞墙，倒是撞出一条我一开始没想到的东西。这篇文章没有什么新 SOTA，就是三次实验的真实数据、能跑起来的代码，和一个我现在比较确定的想法：**想让系统记住东西，关键不在怎么"感知"，而在怎么"强制执行"。**

做持续学习或者 Agent 记忆的话，这些坑你可以绕着走。

## 第一次：冻结了梯度，参数还是会动

第一个项目叫 FIP，做的是灾难性遗忘——Transformer 连着学好几个任务，怎么保证学第 N 个的时候不把前面的忘了。

我当时的想法很自然：遗忘就是参数被新任务的梯度改了，那把重要的参数冻住不就行了。

做法是给每个参数算个重要性，重要的标成 stable，反向传播的时候用梯度 hook 把这些参数的梯度清零。梯度是零，参数不动，旧知识留住。我加了 Top-K 稀疏激活、一套状态机、任务结束按重要性固化，单元测试 21 个全过，挺满意。

然后跑了个 sanity check：故意冻结一批参数，只清梯度，训练几十步，再看这些参数动没动。

动了。

| 冻结方式 | 冻结参数的最大漂移 |
|---|---:|
| 梯度 hook（梯度清零） | 9.94e-05 |

不是 bug，代码我翻了好几遍。后来才想明白一件教科书不太提、但很要命的事：**AdamW 不是靠梯度更新的。**

两个原因：

- 解耦权重衰减。每一步都直接给参数乘 `(1 - lr × weight_decay)`，跟梯度是不是零没关系。梯度清零了，权重衰减照样把参数往零拉。
- 历史动量。Adam 里存着过去梯度的滑动平均，当前梯度是零，只要历史动量不是零，参数还会被惯性推着走。

所以我那个"梯度清零"，冻住的只是梯度，参数被另外两股力量悄悄挪动。我以为门锁了，其实人是从窗户进来的。

### 怎么解决

想通了反而简单：别拦梯度，直接在优化器更新完之后，对参数的实际增量做投影。

写了个 `FeatureMaskedAdamW`，在 `step()` 之后加一步：

```
parameter = parameter_before + mask × (adamw 算出的增量)
```

stable 参数的 mask 是 0，不管 AdamW 内部怎么折腾，最终增量强制归零。顺手把它们的动量也清了。

再测：

| 冻结方式 | 冻结参数的最大漂移 |
|---|---:|
| 梯度 hook | 9.94e-05 |
| 优化器 delta 投影 | 0.00 |

这次是真冻住了。

**这件事让我记住的第一点：我以为控制了，和真控制了，差着一个执行层。** 梯度只是优化的一个输入，真正决定参数的是优化器内部那套状态——动量、方差、权重衰减。想强制执行一个约束，得在约束真正生效的那一层动手。

当时我以为这只跟 AdamW 有关。后来发现不是。

## 第二次：机制全对，就是打不过简单的基线

修好冻结的问题，我把完整的 FIP 跑起来跟基线比：普通微调、EWC、5% 回放、稀疏微调。协议提前定死，6 个可控合成任务，token、步数、学习率都一样。

结果挺难看：

| 方案 | 平均遗忘（越低越好） |
|---|---:|
| E 稀疏全量微调（基线） | 0.456 |
| F FIP（我的） | 0.492 |
| C 5% 回放（最强基线） | 0.253 |

我的 FIP 比"什么都不加的稀疏微调"还差。门槛是比基线降 50%，我没降反而更差。

不死心，往下挖，发现遗忘的主战场根本不在我守着的 FFN 参数，在 embedding、attention、norm 这些我没管的地方。于是把重要性保护扩到所有非 FFN 参数（改叫 GPP），这次有用了——遗忘降到 0.312，新任务学习 100% 保留。

但在另一个更简单的基准上，GPP 还是只有边际改善，打不过"BGE 嵌入 + 全量微调"这种简单组合。而且结果对步数、学习率特别敏感，1000 步全崩，400 步才有点优势。

**第二点：机制没有绝对好坏，就看是不是打在瓶颈上。** 我的重要性保留机制本身没问题——后来消融证明智能分配比随机分配好 25.7%。但它解决的"FFN 参数遗忘"在这任务里不是主因。我在一个不是瓶颈的地方造了把精巧的锁。

这是做研究最容易掉的坑：爱上自己的机制，然后到处找它能解决的问题，而不是先看问题的瓶颈在哪。

## 第三次：搬到 Agent 记忆，剧情重演，但这次找到了基线暴露问题的地方

前两次撞完，我注意到一件事：选择性保留这个问题，不只在参数空间有。

现在做 Agent 都在被记忆折磨——上下文一满就忘，跨会话什么都不记得。常见做法之一是用 RAG：把抽取后的信息写入存储，用的时候按语义检索。成熟的 RAG 当然可以有 upsert、版本字段和过滤；本文比较的是一个明确的“追加写入 + 向量 top-k”基线，并检验把更新语义显式放在写入层的取舍。

今年 BEAM（ICLR 2026）有个结论挺反直觉：**长上下文不等于长记忆。** 上下文堆到 100 万 token 照样退化。真正难的是知识更新和矛盾解决——用户改了个事实，系统得忘掉旧值用新值。

这里有个经常被遗漏的点：**只做追加向量写入的 RAG 解决的是“存了之后怎么找回来”（读），却没有自动定义“什么值得存”和“旧值如何失效”（写）。**

若把“用户住北京”和“用户现在住深圳”直接追加为两条向量，它们没有新旧关系。检索时语义几乎一样；除非系统另外写入版本字段、时间排序或覆盖规则，否则它不知道哪条该淘汰。

矛盾解决，这不就是参数空间的灾难性遗忘换了个壳。我把前面那套"重要性驱动 + 选择性保留 + 执行层落地"搬到 Agent 记忆上，叫 IGM（Importance-Gated Memory，重要性门控记忆）。

先说一句：IGM 不是替代 RAG 的，是装在 RAG 前面的写入层。RAG 管读，IGM 管写。你可以把它接在任何现有 RAG 前面：

![标准 RAG 与 IGM 写入层架构对比](fig1_rag_vs_igm.png)

向量库和检索那端没变，IGM 动的只是写进去什么。

### IGM 做了什么

还是那套思路，落到记忆上变成三件事。

**写入闸门**：不是什么都记。每条候选记忆算个重要性，重要的才写。这个重要性是可学习的打分器算的——用手写规则生成弱监督标签（"我的X是Y"是事实=正例，闲聊是负例），训了个 logistic 回归。权重很可解释：

| 特征 | 权重 | 含义 |
|---|---:|---|
| 事实密度（是不是"我的X是Y"） | +3.59 | 最强正信号 |
| 第一人称（"我"） | +2.61 | 关于用户的才值得记 |
| 是否疑问句 | -4.23 | 最强负信号：问题不是记忆 |
| bias | -2.28 | 默认不写（高阈值） |

在小型受控负载里，门控会过滤闲聊并减少写入。但它本身不是通用准确率提升：是否有用取决于抽取质量、查询类型和容量约束，后面的公平消融会把“门控”和“覆盖”分开。

**slot 覆盖**：写入时从"我的X是Y"里抽出属性 X 当 slot，同 slot 的新值直接取代旧值。它把记忆明确建模为当前状态；当前值查询不必在多条旧版本中再判断新旧。

**执行层兜底**：检索不只靠向量相似度，还按 slot 精确路由。

### 又撞墙了

拿它跟标准 RAG 比——BGE 嵌入 + 全量写入，就是随便一个向量库加个好嵌入搭出来的记忆系统，现在大部分 Agent 就是这么干的。

简单场景下我又输了。BGE 太强，标准 RAG 全量存储也能答对几乎所有问题，我的"少而精"没有精度优势，只剩"省内存"这个没人关心的卖点。

这里得诚实：如果你的场景 RAG 全量存储就能搞定，IGM 的精巧就是多余的。这不是 RAG 的错，是我不该在 RAG 的主场（简单事实召回）跟它硬碰。第三次撞墙，撞的还是同一个道理——别在对手足够好的战场上打。

### 但这次把问题收窄成了一个可检验的取舍

前两次都是在基线够好的地方硬碰，输得不冤。这次我不再试图证明“IGM 比 RAG 准”，而是设计一个受控场景，问一个更具体的问题：连续更新时，系统应保留全部版本，还是压缩成当前状态？

场景：同一个属性连续更新 5 次，新旧值语义接近。比如“最喜欢的颜色”，蓝色→青色→蓝绿色→绿色→紫色，一路改。然后问当前值，另问上一次的值。每条链额外加入 24 条互不冲突、需要长期保留的事实。

我把 5 条可读案例扩展为每个 seed 500 条随机化链：从 5 个属性、每属性 20 个手工候选值中无放回抽取 5 个值。所有方法使用相同 BGE 和原始输入；回答步骤用规则读取记忆，不调用 LLM。除了原始追加存储，还加了一个关键消融：**门控但保留版本**。它逐 turn 复用 IGM 的同一门控决定、同一抽取器和同一嵌入，唯一不做的是 slot 覆盖。

| 方法（BGE，28 条容量条件） | 当前值 seed 1337 | 当前值 seed 42 | 历史值 | 持久化事件/记录 | 当前投影 |
|---|---:|---:|---:|---:|---:|
| 原始全量，语义 top-1 | 22.8% (114/500) | 23.2% (116/500) | - | 52 | 52 |
| 原始全量，属性 + 时间 | 100% (500/500) | 100% (500/500) | 100% | 52 | 52 |
| 门控但保留版本，属性 + 时间 | 100% (500/500) | 100% (500/500) | 100% | 32 | - |
| 破坏性 IGM（slot 覆盖） | 100% (500/500) | 100% (500/500) | 0% | 28 | 28 |
| **Versioned IGM（事件 + 当前视图）** | **100% (500/500)** | **100% (500/500)** | **100%** | **32** | **28 个事件引用** |

这个结果比原先的“IGM 100%”更重要，也更不讨巧：**IGM 没有独占当前值准确率。** 只要版本库有属性和时间语义，保留全部版本、或先门控再保留版本，都能答对当前值。

破坏性 IGM 的明确交换是删掉 4 条过期版本，把门控后的 32 条记录压到 28 条，并且不再能回答历史问题。于是我又实现了 Versioned IGM：每个被门控接受的事实作为不可变事件保留，`current_by_slot` 只是指向最新事件的当前状态视图。它恢复了历史查询，两个 seed 的当前值和历史值都是 500/500；但它持久化的仍是 32 个事件，并没有神奇地把总存储压成 28。一个有二级索引的普通版本库也可以把当前查询路由到一条最新记录。因此这是状态视图加事件归档的工程构架，不是“IGM 胜过版本化 RAG”的证据。相同 28 条容量下，门控 FIFO 仍能保住 23/24 条背景事实，破坏性 IGM 和 Versioned IGM 都是 24/24；这是小而可测的差异，不是压倒性胜利。

![原始 5 条手工更新链的机制示意，不是随机化负载的统计图](fig2_decisive_experiment.png)

**第三点：检索之外还要定义更新和遗忘。矛盾解决的关键是把状态/版本语义说清楚。** 只依赖语义 top-k 时，当前值容易被语义近似的旧值干扰；但补救既可以在读侧做属性+时间排序，也可以在写侧做覆盖。前者保留审计历史，后者压缩为当前状态；Versioned IGM 则把两者拆为当前状态视图和事件归档。三者的代价不能混成一个“准确率”。

完整配置、原始 JSON 和限制见 [受控更新记忆：公平消融与负载扫描](MEMORY_DECISIVE_LOAD_SWEEP.md)：模板化中文句式、有限候选池和重复背景事实意味着 500 条不是 500 个独立真实用户样本，更不能外推成通用 RAG 排名。

## 后来：把它做成了 DeepSeek Harness 的一个插件

实验做完后，我把这套写入层做成了 **DeepSeek Harness（dsh）的插件** `dsh-igm-memory`，想看看它在真实 agent 环境里是不是也成立。

dsh 是开源 agent harness（cordis 插件架构）。我写了一个插件，给 agent 加了两样东西：

- **`remember_fact` 工具**——agent 想记事实时调用它，走 IGM 闸门（闲聊/问句被拒）+ slot 覆盖（同属性新值取代旧值）。
- **`recall_fact` 工具 + 会话启动注入**——agent 开局就能看到此前会话记住的事实，也能主动查。

真实测试里最有意思的一幕：我在一个会话里让 agent"记住住址是北京"，再"改成深圳"，然后**开一个新会话**直接问"我住址是哪"。agent 的回答是"你的住址现在是深圳"——它在新会话开局就看到了注入的持久化记忆，且只看到深圳（北京被覆盖了）。

这是写入层的一种现实化行为：**若 agent 只是追加记忆文件，就会留下北京和深圳两条版本；IGM 选择只暴露当前的深圳。** 这适合“当前状态”产品，不替代需要审计历史的版本存储。

插件是开源的（`dsh-igm-memory`，MIT），完整实现：写（闸门+覆盖）、读、跨会话注入、JSON 持久化、遗忘（consolidate）。版本状态也要说准：本文的 Versioned IGM 原来是 `memory_arch/` 里的独立原型，现在已下沉为 `igm` 库和插件的默认覆盖语义（旧值关闭有效期进归档，`supersede="delete"` 才恢复原来的就地删除）。读出口两边都有——库是 `mem.history(slot)` / `mem.previous(slot)`，插件是 `recall_history` 工具，问"之前是什么"就返回该属性的版本时间线。

## 撞三次墙，搞清楚的三件事

**1. 我以为控制了，不等于我控制了——约束要下在执行层。** 梯度 hook 冻不住参数，因为 AdamW 靠动量和权重衰减更新。RAG 检索分不清新旧，因为语义近似的值在向量空间重叠。任何"选择性保留"的系统都得问一句：约束是下在"感知/读取"那层，还是"真正生效/写入"那层？大部分人下错了层。

**2. 机制没有绝对好坏，就看是不是打在瓶颈上。** 我的重要性保留机制，FFN 参数上输了（不是瓶颈），非 FFN 参数上赢了（是瓶颈），简单记忆场景输了（RAG 够用）。在受控更新场景，它没有“赢过版本库”：破坏性 IGM 把产品语义改成“只留当前状态”，Versioned IGM 只是把这层状态投影和版本归档显式实现。别爱上锤子，先看钉子在哪。

**3. 重要性驱动的选择性保留是个能迁移的范式。** 这是我最大的收获。从参数（FIP/GPP）到记忆（IGM），同一个结构反复出现：用重要性信号筛选，在执行/写入层强制保留或淘汰，让系统随时间只积累真正重要的东西。可以是优化器里的 delta 投影，也可以是 RAG 写入层的 slot 覆盖。形式不同，内核一样——感知重要性是辅助，强制执行才是本体。

## 什么时候别用

不想写成"我搞了个厉害的东西"，所以说清楚它什么时候没用：

- 标准 RAG 够用时别加这层。覆盖默认是归档式的：历史不会因为更新而丢失，`mem.history(slot)` 就能答“上一次是什么”，代价是事件库随同属性更新次数单调增长，只有 consolidate 会物理清除。需要真正的版本审计和二级索引时，带版本字段 + 时间排序的存储仍然是更成熟的方案。
- 读取层能够解决当前值时，属性过滤 + 时间排序是直接且强的方案。写入层要解决的其实是一件很小的事：让"当前"这个语义在存储里存在，而不是散落在读侧的排序规则里。
- IGM 是 RAG 的增强件，不是替代品。复用同一个向量库同一个嵌入，写入侧加筛选和覆盖，接在前面就行。
- 实验是受控合成数据上做的，记忆基线是 4B 本地模型，不是 GPT-4。方向我有信心，绝对数字别当真——真实大规模数据上所有方法表现都会变。

## 复现

代码和数据都开源了（合成数据，不依赖被墙的外部源），关键实验几分钟能跑完：

```bash
# 500 条随机化受控更新负载（不调 LLM）
python -m memory_arch.run_decisive --embed-backend bge \
  --background-facts 24 --full-capacity 28 \
  --random-trials 500 --updates-per-chain 5 --seed 1337
# 输出：追加 top-1 约 0.23；属性+时间、门控版本库、破坏性 IGM 和 Versioned IGM 的当前值均为 1.00
```

训练可学习的写入打分器：

```bash
python -m memory_arch.train_scorer
# held_out ≈ 0.956，权重可解释
```

## 最后

没做出刷榜的系统。但撞完这三堵墙，我对"怎么让 AI 记住东西"的理解比开始时深了不少。

做类似东西的话，希望这三堵墙有用。别只在读取/信号层雕花了，去写入/执行层下硬约束。

有不同看法或者觉得我哪想错了，评论区聊。我挺想知道两件事：你的 RAG 系统怎么处理事实被更新？旧值是留着、覆盖、还是没想过？还有——你的系统里，现有基线在哪种可复现实验中会稳定暴露问题？找到它，比造个精巧的机制重要。
