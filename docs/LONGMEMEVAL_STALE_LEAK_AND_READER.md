# LongMemEval-S：陈旧值泄漏、写入层覆盖度与 reader 评测

> 状态：E1/E2 已完成；E3（reader）见文末，数字待本次运行落盘。所有报告在 `reports/` 下可按文件名复核。

## 为什么做这三件事

已有的 [LongMemEval-S 检索报告](LONGMEMEVAL_S_RETRIEVAL.md) 只回答一个问题：**带标注的证据 session 是否进入 top-k**。它看不见三件事，而这三件事恰好决定了 IGM 这类写入层的价值是否在真实数据上成立：

1. **top-k 内部的顺序。** 知识更新题的证据是两条 session（旧值 + 新值）。召回指标只要两条都在集合里就算满分，但 reader 是按顺序读的——先读到旧值就是一次陈旧泄漏。
2. **答案级后果。** 检索召回不等于答对。没有 reader，就不知道"先读到旧值"到底有没有害。
3. **写入层的前门。** slot 抽取规则写在中文模板上（`我的{ATTR}是{V}`）。换成自然对话，这条规则还成立吗？这是合成负载永远测不到的问题。

另外补一个长期存在的短板：此前所有 LongMemEval 数字都用中文 BGE 编码英文。本次下载了 `bge-small-en-v1.5`，E1 与检索指标都在两种编码器下重跑，结论以英文编码器为准。

## E1：真实数据上的陈旧值泄漏

方法（`python -m memory_arch.run_stale_leak`）：

- 取 knowledge-update 题（全量 78 条，其中 72 条有两条证据 session）。
- 判定哪条是"新"：包含 gold answer 文本的那条（`answer_text`，45 条）；判定不出时退回"日期较晚者为新"（`date_order`，27 条）。两条路径分开报告，因为后者依赖一个假设。
- 用与检索报告相同的编码器与排序（user-only session 文档、recency 权重 0 与 0.02）。
- 指标：`stale_above_new@k`（旧值排在新值之前）、`new_missing@k`（新值不在 top-k）、`leak@k`（二者之一）、MRR（新值的排名倒数）。

**英文编码器，`recency_weight=0`（= 现有读侧选定的策略）：**

| 指标 | 全量 (n=72) | `answer_text` 子集 (n=45) | `date_order` 子集 (n=27) |
|---|---:|---:|---:|
| leak@1 | 63.9% | 64.4% | 63.0% |
| leak@10 | 62.5% | 64.4% | 59.3% |
| stale_above_new@10 | 61.1% | 62.2% | 59.3% |
| new_missing@10 | 1.4% | 2.2% | 0.0% |
| MRR（新值） | 0.649 | 0.634 | 0.673 |

**对照：中文编码器（此前报告的编码器）**：leak@1 61.1%、leak@10 48.6%、stale_above_new@10 47.2%、MRR 0.600。

**加 recency 先验（0.02）之后（英文编码器）**：leak@1 55.6%、leak@10 54.2%、MRR 0.693。分层看，recency 只修好了 `date_order` 子集（leak@10 59.3%→37.0%），对 `answer_text` 子集**完全无效**（64.4%→64.4%）——也就是说，对真正发生了取值变化的那批题，时间先验救不了排序。

结论：

- **正确证据几乎总能被召回（new_missing@10 = 1.4%），但它在 61% 的题里排在自己的前驱后面。** 换用更强的英文编码器后泄漏不减反增（leak@10 48.6%→62.5%），因为好编码器把新旧两条都召回得更全，而两者的顺序近乎随机。
- 这是召回类指标**结构上**看不见的失败模式：**同一批 knowledge-update 题，`recall_all@10 = 98.31%`（英文编码器），而按序读取的 reader 在 62.5% 的题里先遇到旧值。** 两条 session 都在 top-10 里，顺序是错的。
- 没有免费的读侧修法：recency 先验只对"较晚写入即更新"的那半边有效。

## E1 附带：编码器一换，已发表的检索结论有两处变化

同一 test 分区、session 级 `recall_all@10`：

| 读侧策略 | 中文 BGE | 英文 BGE |
|---|---:|---:|
| user-only | 86.91% | **93.98%** |
| role-aware（38 条助手历史路由） | 87.43% | **93.98%** |

- 换编码器带来 **+7.1pp**（user-only）。
- `recall_all@10` 在英文编码器下对两种策略都饱和（93.98%），所以 k=10 这个口径**不再能区分**二者——旧结论的 +0.52pp 看起来"归零"，其实是天花板效应。**角色路由的收益没有消失，它转移到了排序指标上**：整体 `recall_all@1` 27.75%→28.80%（+1.05pp）、`nDCG@5` 88.87%→89.75%；而被路由命中的目标题型 `single-session-assistant` 在 `recall_any@1`/`recall_all@1` 上是 86.05%→95.35%（**+9.3pp**）。也就是说，此前把它读成"召回改进"是弱编码器下的口径错误；按排序口径它是对目标题型真实且集中有效的改进。

## E2：写入层的前门在自然文本上不成立

方法（`python -m memory_arch.run_write_coverage`）：把现有 slot 关系模式**直译**成英文（`my X is now Y`、`I changed my X to Y`、`I set my X to Y`、`the X I use is Y`），在写成代码之前就冻结，避免对同一份语料调参后自证。语料是 LongMemEval-S 的全部 12.2 万条 user turn 与 knowledge-update 的 72 组新旧证据对。

| 指标 | 结果 |
|---|---:|
| 现有（中文）规则在英文自然文本上命中 | **0 / 122,416** |
| 英文直译规则命中 | 61（0.0498%），45 个不同键 |
| knowledge-update 组对里新旧两侧抽到**同一个键** | **0 / 72** |

人工过了一遍全部 45 个键（不是抽样）：约三分之一像真属性（`supervisor's name`、`favorite instructor`、`phone's ringtone`、`zip code`、`annual salary`、`personal best`），其余是习语、错段与残句——`changed my mind`→`mind`、`changed my home to san francisco`→`home to san francisco`、`set up Habitica to`→`up habitica`，还有 `mom`/`sister`/`colleague` 这类把"人"当成了属性。

结论：

- 规则不是"在英文上弱一点"，而是**在自然叙述里没有可抽的属性键**。真实更新长这样：`I've tried four different ones so far`（值在叙述里，键不在）、`I hope to beat my personal best time of 25:50`（键要靠"personal best time"这个短语才知道）、`my mom is actually using the same grocery list app as me now`（状态变化，没有 `X 是 Y` 的形状）。
- 所以 IGM 的 slot 机制不需要更好的英文正则，它需要**另一种键来源**：读侧问题派生（question-derived key）、嵌入聚类，或让 LLM 给候选事实命名属性。表层句法键这条路在自然对话上封死了。
- 这也解释了合成负载为什么必须存在：它的模板形状就是这个机制的前提。**IGM 作为"事实库写入层"（个人助理的显式记住、项目约定这类被主动陈述的状态）成立；作为"通用对话记忆层"不成立。** 这是范围界定，不是实现缺陷。

E2 的英文模式集**没有**进入 `igm/gate.py`：0.05% 命中率、0% 键稳定性、约三分之二是假阳，按这个数据发布它只会扩大维护面（三份实现的 parity 成本）而不解决任何问题。

**真实使用数据的印证**：DSH 插件在这台机器上留下的 7 个真实存储文件（`~/.dsh/storages/igm-*.json`，5 个项目域 + 用户域）共 13 条记忆，其中 3 条带 slot——`住址`、`常用语言`、`包管理器`，全部是被主动陈述的状态，没有一条来自自然叙述。这正是本节的"事实库写入层"范围界定。这些文件写于改造之前，用新代码载入后全部正确视为当前有效、`eventId` 唯一分配、原文件未被改写（v1 升级路径在真实数据上验证通过）。样本量太小，不足以支撑写入置信度研究——那需要长期积累的真实更新对。

## E3：reader-in-the-loop 结果

设计（`python -m memory_arch.run_reader_eval`）：

- reader：本地 Qwen3-4B（HF bf16，思考开启，768 token 预算）。本地 GGUF 那版的 `/no_think` 无效，且 `LocalLLM.chat` 在 `</think>` 处截断会丢掉答案，因此没有复用 `LocalLLM`。
- 证据：turn 级检索（user turn 为文档），k=8。
- 三个臂，**只改一个因素**：
  - `ranked_k8`：按相似度取 top-8，按排名顺序呈现，不给日期。
  - `chrono_k8`：**同一组 8 条**，改为按时间顺序呈现。集合不变，只改顺序。
  - `oracle`：标注证据 session 的 user turn，按时间顺序。reader 的上界。
- 控制组：其他题型分层各 12 条（共 60），走 `ranked_k8`。
- 打分：字母数字归一化的 containment（比 `run_m0.score` 有意放宽），非官方评审器，不用 LLM judge。未产出答案的截断行单独标记并从主准确率中排除。

**knowledge-update，n=72 每题每臂：**

| 臂 | 全部行准确率 | 有效行准确率 | 截断率 | 上下文 token 均值 / p95 | 答案 token 均值 |
|---|---:|---:|---:|---:|---:|
| `ranked_k8`（现状：按相似度排序） | 47.2% | **41.3%** | 12.5% | 478 / 647 | 366 |
| `chrono_k8`（**同一组证据，改时间序**） | 63.9% | **65.2%** | 8.3% | 478 / 647 | 325 |
| `oracle`（标注证据，时间序） | 65.3% | **66.7%** | 8.3% | 647 / 848 | 310 |
| 控制组（其他题型，`ranked_k8`） | 20.0% | 20.8% | 20.0% | — | — |

结论：

- **E1 的排序泄漏确实会变成错误答案，量级很大：同一组证据、只改呈现顺序，准确率从 41.3% 升到 65.2%（+23.9pp）。** 这个差异在 n=72 上远超噪声（二项 SE ≈ 5.7pp）。
- **时间序几乎追平 oracle（65.2% vs 66.7%）**：检索集合本身没问题，问题就是顺序。也就是说这个失效不是"没找到"，而是"找全了却按最误导的方式排"。
- **修法在读侧的 prompt 组装，不需要写入层、不需要 LLM 抽取、不需要更好的编码器**：把召回的 turn 按时间升序放进上下文，让"最新的一条在最后"这个位置先验替模型做掉新旧判断。真实系统的会话/消息本来就有时间戳，所以这是可部署的。
- 位置先验的方向值得注意：`chrono_k8` 把最新陈述放在**最后**。这与 LLM 的 recency bias 一致——读侧可以主动利用它，而 IGM 的写法（只留当前值）是在写入侧消除同样的问题。两条路指向同一个目标，E3 说明在读侧做更便宜。
- 控制组 20.8%（`single-session-user` 60%，`temporal-reasoning`/`single-session-preference` 0%）说明这个 4B reader 在其他题型上明显更弱；KU 题恰好是"短取值 + 明确属性"的形态，所以它有足够余量暴露臂间差异。
- **一个设计缺陷要写明**：k=8 时 72 题里有 71 题的上下文都包含旧值那条（陈旧证据几乎普遍存在），所以原计划用 `leak_in_context` 做的 2×2 分层在这批数据上没有区分度。E1 已经用 72 题的排序指标覆盖了同一件事，但"泄漏与否"这一层的归因没做出来。

### E3b：把归因补上（三个新臂）

因为 k=8 时陈旧证据几乎普遍存在，改用**直接干预**而不是分层：只给陈旧证据、只给当前值、以及把同一组证据倒过来。同样 72 题、同一 reader。

| 臂 | 全部行准确率 | 有效行准确率 | 截断率 | 上下文 token |
|---|---:|---:|---:|---:|
| `stale_only`（只给陈旧 session 的陈述） | 4.2% | **4.4%** | 5.6% | 318 |
| `reverse_k8`（同一组 8 条，**newest-first**） | 29.2% | **13.8%** | 19.4% | 478 |
| `ranked_k8`（相似度序，现状） | 47.2% | **41.3%** | 12.5% | 478 |
| `current_only`（只给更新后的陈述） | 58.3% | **58.8%** | 5.6% | 327 |
| `chrono_k8`（同一组 8 条，时间序） | 63.9% | **65.2%** | 8.3% | 478 |
| `oracle`（标注证据，时间序） | 65.3% | **66.7%** | 8.3% | 647 |

解读：

- **陈旧证据是近乎确定性的毒药**：只看到被取代的陈述时，reader 只有 4.4% 的概率给出当前值——它完全跟着给出的证据走，不会自己怀疑"这条可能过时了"。这量化了泄漏的孤立危害。
- **效应精确地是"最新一条放在最后"，不是"任何一种有序"**：把同一组证据倒成 newest-first 是 13.8%，**比任意顺序的相似度序（41.3%）还差**，而时间序（newest-last）是 65.2%。同一个集合，方向反了差 51.4pp——这与 LLM 的位置/近因偏置一致，且说明读侧可以主动利用它。
- **免费的读侧修法不输理想写入层**：只给当前值（模拟"写入层只留最新版本"的完美实现）是 58.8%，反而低于时间序组装的 65.2%——因为保留其余上下文有助于 reader 确认取值。也就是说，**不需要写入层就能拿到比写入层上界更好的结果**。
- 截断行集中出现在困难臂（reverse 19.4%），而截断行的 thinking 文本常含正确答案、会被 containment 误判为对，所以 `accuracy_answered` 是本实验的主指标；`accuracy` 列仅作披露。

一个诚实的方法论标注：`stale_only` 的 4.4% 不是"reader 能力"，而是"证据被污染后的必然结果"——这正是要测量的东西。

## 这些结果把解法空间收缩成了什么

E1、E2、E3 合起来排除了四条便宜路，验证了一条，剩下的两条都贵：

| 候选解法 | 结论 |
|---|---|
| 更好的编码器 | 排除。换英文 BGE 后泄漏不减反增（48.6%→62.5%）：好编码器把新旧两条都召回得更全，顺序反而更随机。 |
| 时间先验（打分层面） | 基本排除。只对"较晚写入即更新"的 `date_order` 子集有效（59.3%→37.0%），对真正发生取值变化的 `answer_text` 子集无效（64.4%→64.4%）。 |
| 表层句法键（英文正则） | 排除。命中 0.05%、键复用 0/72、约 2/3 假阳。自然更新没有可抽的键。 |
| 问题派生的键 | 排除。同一属性的新旧两句语义几乎相同，问题与两条的相似度都高——这正是读侧排序分不出来的原因。 |
| **把召回证据按时间序组装进 prompt** | **有效（E3）：+23.9pp，且几乎追平 oracle。不需要改检索、不需要 model 抽取，只用现成的时间戳。** |

剩下两条是重方案，且 E3b 已经给第一条设了上界：

1. **写入期用 LLM 做事实抽取与更新判定**（而不是正则）。E3b 的 `current_only` 臂就是这件事做到完美时的样子——只把当前值交给 reader——结果是 58.8%，**低于免费的时间序组装（65.2%）**。所以它的价值不在答案准确率，而在别处：只保留当前值能把存储与 prompt token 压下来（327 vs 478 token），并且给出可审计的"当前状态"语义。要论证它值得引入，得用 token 成本、审计需求和冲突消除来论证，不能用准确率。
2. **读侧显式检测更新关系**：不是排序，而是让模型看到"这两条是同一件事的早晚版本"这类标注。它需要一个能识别更新关系的组件，本质上还是模型能力，只是搬到了读侧。E3b 说明这条的必要性存疑——顺序本身已经吃掉了几乎全部差距（65.2% vs oracle 66.7%）。

还有一件 E2 没能覆盖但值得单独做的问题：**写入置信度**。当前实现一旦抽出 slot 就遮蔽旧值，没有"不确定就两个都留"的档位。要研究它，需要一批真实的、发生在事实库形态上的更新（而不是 LongMemEval 的叙述式对话）——最现实的来源是 DSH 插件自己的存储（`~/.dsh/storages/igm-*.json` 里已经有真实使用产生的 slot 更新），那是下一个数据收集任务，不是本文的实验。

## 边界

- 泄漏判定依赖 gold answer 文本或日期顺序；`answer_text` 子集（45/72）完全不依赖日期假设，是这批结论的稳健性依据，两套子集结论一致。
- `new_missing@1` 这类单条指标在 n=72 上置信区间宽；文中只把 ≥10pp 的差异当信号。
- E2 是单标注者审计（全部 45 个键，非抽样），且英文模式集是"直译"而非"最优英文规则"——它给出的是这一族规则的上界量级，不是精确上界。
- E3 的 4B reader 弱于 LongMemEval 官方用的模型，绝对准确率不可与榜单比较；它只用于**臂间对照**。控制组是这一点的守门指标。
- LongMemEval-S 的会话本身由模型生成，是"自然叙述"的近似而非真实用户日志。
